# Hosting Good Faith on Render and Supabase

The steps, in order, to take the app from a laptop to a URL the judges can open. Nothing in this file has been run against a live host yet; it is the plan for the first deploy, written so each step is one screen. `render.yaml` in the repo root describes the service.

## Before you start

- Accounts: GitHub (the repo goes public, with the MIT license in `LICENSE`), Render (a paid Starter web service), Supabase (free), PayPal Developer (sandbox), and the Anthropic console (an API key with a spend limit).
- **The hosted app sits behind an access code** (section 8): every landlord page and API route needs the session the `/access` page sets, and the Claude jobs, sandbox invoices and new demo copies have daily limits. Each browser that enters the judges' code gets its own private copy of the demo landlord (section 9), so judges never see or change each other's work, or yours. The code is shared by the judges, so it is a demo gate, not a landlord sign-in: host the fictional demo data only, never a real tenant, and keep `PAYPAL_ENVIRONMENT=SANDBOX`. The close-out routes still refuse `LIVE` (`src/lib/agent.ts`). The tenants' pages (`/t/<token>`) stay open to their token, as before.
- The laptop keeps two jobs: filling the pool of pre-paid sandbox deposits (`npm run demo:pool`, section 9), which pays PayPal invoices with Playwright, and, until a cron job does it, removing old demo copies (`npm run demo:sweep`).

## 1. Supabase

1. supabase.com > New project. Name `deposit-agent`, region **West US (North California)** (closest to the landlords), a strong database password (the app never uses it; the API key does the work). Note the region: the Render service goes next to it (step 4.2).
2. SQL Editor > New query. Paste `supabase/migrations/20261001203558_initial_schema.sql` and Run. Repeat for every file in `supabase/migrations`, in filename order (the version prefix is the order). The later files add the daily limits (`daily_usage_limits`, `usage_limits_tenancies_uploads`, section 8) and the private demo copies (`workspaces`, `demo_templates_and_deposit_pool`, `demo_copy_functions`, `demo_copy_dates_never_earlier`, `demo_copy_review_fixes`, `demo_texas_template`, `demo_texas_template_moves_out_at_lease_end`, section 9; the last one only re-dates this project's own Texas template and changes nothing on a fresh project), the tenants' disputes, the two-agent negotiation and the settlement (`disputes_and_tenant_advocate`, `send_dispute_waits_for_the_advocate`, `negotiation_and_settlement`, `settlement_review_fixes`), the settled dispute a demo copy's closed unit shows as history (`demo_settled_history`, `demo_history_guard`, section 9), and PayPal's webhooks (`paypal_webhooks`, `paypal_webhook_review_fixes`, section 2.5). The SQL editor is the one path used here: the Supabase CLI's `db push` needs a `supabase/config.toml` the repo does not carry, and it records what it applied in a table the SQL editor does not, so mixing the two later re-applies files.
3. Check the result. Table Editor shows `properties`, `tenancies`, `photos`, `payments`, `audit_log`, `deductions`, `agent_runs`, `tenant_links`, `daily_usage`, `workspaces`, `demo_templates`, `demo_template_history`, `demo_deposit_pool`, `demo_copy_usage`, `disputes`, `negotiation_turns`, `settlements`, `paypal_webhook_events` and `paypal_disputes`, every one with RLS enabled and no policies. `workspaces` holds one row of kind `owner`. Storage shows three buckets, `leases`, `photos` and `receipts`, all Private (the first and third migrations create them). Database > Functions shows `set_notice`, `remove_notice`, `set_tenant_move_out`, `create_tenant_link`, `take_usage`, `create_demo_copy`, `create_demo_copy_with_history`, `copy_demo_history` and the other demo-copy functions, and the dispute's (`send_dispute`, `claim_advocate_run`, `claim_negotiation_run`, `negotiation_turn`, `accept_settlement`, `claim_settlement`, `finish_settlement`) and the webhook's `claim_paypal_event` and `merge_payment`, executable by `service_role` only.
4. Project Settings > API Keys > Secret keys: create one (or reveal the default) and copy it. That is `SUPABASE_SECRET_KEY` (it starts with `sb_secret_`). The Project URL on the same page (`https://<ref>.supabase.co`) is `SUPABASE_URL`. Never the publishable key: with RLS on and no policies it can read nothing, and the app would not work with it.
5. Storage settings: the default per-file upload limit (50 MB on the free plan) is far above what arrives; the browser sends photos at 2000 px, under 1 MB each.
6. Free-plan caveat: a free project **pauses after seven days without activity**, and a paused project makes every page fail. During judging either open the site a couple of times a week, restore the project from the dashboard before the judges look (it takes a minute or two), or move it to Pro ($25 a month) for that month.

## 2. PayPal sandbox

1. developer.paypal.com > Apps & Credentials > **Sandbox** tab > Create App (or open the default app). Copy the Client ID and the Secret: `PAYPAL_CLIENT_ID` and `PAYPAL_CLIENT_SECRET`. Set `PAYPAL_ENVIRONMENT=SANDBOX`.
2. In the app's Features, keep **Invoicing** and **Payouts** on (Payouts is a checkbox the sandbox grants at once). Refunds come with Accept payments. The Agent Toolkit uses these same credentials.
3. Testing Tools > Sandbox Accounts. The Business account is the app's merchant (created with the app). Create or open a **Personal** account: it plays the tenant who pays the invoice and receives the refund. Its email and password are `PAYPAL_SANDBOX_BUYER_EMAIL` and `PAYPAL_SANDBOX_BUYER_PASSWORD`, used by the demo seed and the deposit pool on the laptop only; they never go to Render.
4. What the sandbox will not do: Payouts to a Venmo wallet are rejected ("Recipient wallet not supported in sandbox", found by `scripts/sandbox_smoke.py`), and the app has no Venmo rail anyway: refunds go to the tenant's PayPal account, as a refund of the original payment or a Payout to the email in the agreement. The sandbox dates a payment the day it is paid, so a statement says the deposit was paid the day it really was (for a demo copy, the day its pre-paid deposit was paid).
5. **Webhooks** (`src/app/api/paypal/webhook/route.ts`, `src/lib/paypal-webhook.ts`). PayPal tells the app when a deposit invoice is paid, a capture completes, is refunded or is reversed, a Payout batch or its payment changes, and a PayPal dispute opens, changes or closes (the app still reads the invoice from PayPal when a page loads and when the agent runs). What each one does:
   - **Checked with PayPal first.** Every delivery goes back to PayPal's verify-webhook-signature, byte for byte, with the five `PAYPAL-*` signature headers and `PAYPAL_WEBHOOK_ID`, before anything in it is read. One that doesn't verify gets a 401 and changes and stores nothing; one that can't be checked (PayPal down) gets a 502 and PayPal sends it again.
   - **Once.** A verified event is recorded by its id in `paypal_webhook_events` (`claim_paypal_event`), with its payload, the workspace and tenancy it went to, and what it did (`applied`, `recorded`, `unmatched`, `ignored`, `failed`). PayPal's retries and a replayed request are answered 200 and not processed again; a try that failed is processed on the next delivery.
   - **One tenancy, in its own workspace.** The event's PayPal ids (invoice, capture, refund, payout batch) are looked up in `payments`. A pre-paid demo deposit belongs to the copy that holds it now (not an old copy that gave it back on Start over), a template's payment to the read-only template (so a copy that shows it never changes, and the template doesn't either), and an id two workspaces hold to neither. Statuses only move forward, so an event that arrives late can't undo a newer one.
   - **What changes.** A paid invoice: the deposit's status and PayPal's transaction (so the next step moves on), an activity entry and the bell. A refund or Payout: its status (a Payout's from its one payment once PayPal reports it: unclaimed, returned), and a sent settlement's PayPal status. A refund made in PayPal rather than here: an activity entry and the bell, and the close-out stays blocked until someone has looked (PayPal's invoice shows money refunded that the app never recorded); there is no button yet to take such a refund in as the tenancy's return, so for now it is settled in PayPal and the database by hand (the dispute round's work). A reversal (a chargeback): on the deposit, which blocks the close-out and a settlement; the ledger and Properties stop counting it as held, and the unit reads "Payment reversed" with "Check PayPal" as its step. A capture that arrives before its invoice's PAID event (which records the capture) is answered 503 for ten minutes, so PayPal sends it again after; later it is stored as unmatched. A PayPal dispute: stored in `paypal_disputes` for the dispute handling to come. Anything else is stored and ignored. Each status PayPal sent reads "From PayPal" in Payments, on the property's Payments tab, the deposit step and the refund receipt, and the bell has a From PayPal section.
   - **The route** sits outside the access gate (`src/proxy.ts`): no session comes with a delivery, and PayPal's signature is its authentication. It takes at most 256 KB, and 120 deliveries a minute per address, 600 in all (in memory, `src/lib/rate-limit.ts`), refused with a 429 that PayPal retries. Only a delivery the app would ask PayPal about counts (an event with all five signature headers): one without them is refused with a 401 for free and never counts, so a flood of junk can't use up the allowance PayPal's real deliveries need. The first 429 logs which header the address came from (`cf-connecting-ip` on Render); if it says `x-forwarded-for`, set `GOOD_FAITH_CLIENT_IP_HEADER`. Values from a delivery are logged quoted and escaped, so an unsigned request can't write a log line of its own.
   - **Writes** to a payment row go through `merge_payment`: the status only while it is still the one the event read, and only the keys the event changed, so two deliveries at once (a capture and a reversal), or a page's refresh and a delivery, keep each other's.

   To turn it on, after the code is deployed:
   1. `node scripts/paypal-webhook.mjs --register` (sandbox only; it refuses `LIVE` and never prints the secret) registers `https://good-faith.onrender.com/api/paypal/webhook` for every event above that PayPal offers the app (`--types` lists them; the sandbox doesn't offer `PAYMENT.PAYOUTS-ITEM.DENIED`, which the app still reads if it comes) and prints `PAYPAL_WEBHOOK_ID=<id>` (PayPal's webhook id, 17 characters such as `0RL55557138754131`). The hosted demo's was registered on 2026-10-05 as `0RL55557138754131`. Run again, it updates that webhook's events instead of making a second one. With no flag it lists the app's webhooks.
   2. Set `PAYPAL_WEBHOOK_ID` in the service's Environment on Render (it is read on each request, so a restart is enough). Until it is set, the route answers 503 to every delivery and PayPal retries each one for three days, so nothing sent meanwhile is lost.
   3. Check it live. developer.paypal.com > Testing Tools > Webhooks Simulator: the webhook's URL, an event type (PAYMENT.CAPTURE.REFUNDED), Send Test. The simulator's events are mock deliveries that PayPal's own verify-webhook-signature refuses, so the route must answer **401** and Render's logs show `PayPal webhook refused: the signature didn't verify`: the forged-event check, passing on the live host, with nothing stored. For an event that verifies, do something real in the sandbox: in a demo copy, Send refund on 1140 E. Juniper Hollow Ln; within a minute the refund's row in Payments reads "From PayPal" (PAYMENT.CAPTURE.REFUNDED) and the bell's From PayPal section says "Refund completed". The developer dashboard's webhook event log lists each delivery with the answer it got and can send one again (a resent event is a duplicate: 200, processed once). In Supabase, `select event_type, status, note, tenancy_id from paypal_webhook_events order by received_at desc limit 10` shows what each did.
   4. On the free plan a sleeping service takes about a minute to wake, so PayPal may give up on the first delivery after a quiet spell; it sends it again later.

   **Idempotency.** Every PayPal write carries a PayPal-Request-Id made from the app's own records, so a retry after a lost answer gets the first result back instead of paying twice. The deposit invoice is the exception: PayPal's Invoicing API ignores the header (tried in the sandbox on 2026-10-05: two creates with one key made two invoices), so it is made once by its invoice number, `GF-` and 20 hex digits of a hash of the tenancy and the invoice's content (`depositInvoiceNumber`), which PayPal refuses to repeat (DUPLICATE_INVOICE_NUMBER, tried the same day). A retry, a double click or a second tab finds the first invoice by its number (search-invoices) and sends it only if it is still a draft; the database keeps one deposit invoice per tenancy, and an invoice with other content (the lease corrected in between) is a new number. The header still goes with the create (the number) and the send (the invoice id). The others: the close-out's refund through the Agent Toolkit from the tenancy, the amount and how many earlier attempts PayPal refused outright (`closeOutRefundKey`; the toolkit sends `context.request_id` as the header), a close-out Payout from its batch id (`deposit-<tenancy>`, which PayPal also refuses to reuse for 30 days), and a settlement from its claim, as before. If a refund went without an answer and the plan then changed (a new key), PayPal's invoice shows money refunded that the app never recorded, and the close-out stops there until someone looks.
6. Going live is a separate decision, not part of the hackathon, and it is blocked until the landlord pages have a real sign-in (one account per landlord, not the shared demo code): `src/lib/agent.ts` refuses to start or approve a run when `PAYPAL_ENVIRONMENT=LIVE`. After the sign-in: a real Business account, Payouts enabled by PayPal's review, the guard removed on purpose, and real fees. The demo seed and the pool script refuse to run against LIVE as well.

## 3. Anthropic

1. console.anthropic.com > API Keys > Create Key, named for the hosted app. That is `ANTHROPIC_API_KEY`.
2. Billing > Limits: set a **monthly spend limit** before the URL is public. Anyone with the access code can upload leases and start close-out runs, and each one spends this key. The app's daily limits (section 8) cap that per session and per day; the console limit is the ceiling behind them. A full demo costs a few dollars (section 6), so $20 covers several full demos; set it at what the judging period needs and no more.
3. Optional: `ANTHROPIC_MODEL` switches every Claude job (lease extraction, the photo inspection, the close-out agent, the tenants' advocate and the landlord's negotiator) from `claude-opus-5-5` to another model. ## 4. Render

1. Push the repo to GitHub, public.
2. Open `render.yaml` and set `region` to the Render region closest to the Supabase project (Supabase dashboard > Project Settings > General > Region): `oregon` for West US (North California), `virginia` or `ohio` for an East US project, `frankfurt` for Europe. Every page makes several database calls, so the distance shows in every load. Commit it.
3. dashboard.render.com > New > Blueprint > connect the GitHub repo. Render reads `render.yaml` and shows one web service, `good-faith`: Node, plan Starter, build `npm ci && npm run build`, start `npm start`, health check `/api/health`, one instance.
4. Render asks for every variable the file lists (they are all `sync: false`, so the file holds no values). Required: `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `PAYPAL_ENVIRONMENT` (`SANDBOX`), `PAYPAL_CLIENT_ID`, `PAYPAL_CLIENT_SECRET`, `ANTHROPIC_API_KEY`, `PAYPAL_WEBHOOK_ID` once the webhook is registered (section 2.5; until then PayPal's deliveries get a 503 and are retried), and the access gate's three (section 8):
   - `GOOD_FAITH_ACCESS_CODE`: the judges' code. A long random string you can type, for example `openssl rand -hex 12`. It goes in the Devpost submission's testing instructions, never in the repo.
   - `GOOD_FAITH_OWNER_CODE`: your own code, different from the judges'. It opens your own data (the owner workspace).
   - `GOOD_FAITH_SESSION_SECRET`: `openssl rand -base64 48`.
   Leave the optional ones empty for their defaults, except two for the judging window (section 8): `GOOD_FAITH_DAILY_AI_TOTAL`, set to what a day of judging needs, for example 40; and `GOOD_FAITH_DAILY_COPIES`, set to 15 or 20. Its default of 5 copies per address a day is low for judges who share one office network or VPN exit: three of them entering the code twice each would be locked out until the next day. A copy costs only rows (and a pool deposit while one is left), and `GOOD_FAITH_DAILY_COPIES_TOTAL` (60) stays the real ceiling. Do not add the sandbox buyer login, `PLAYWRIGHT_PYTHON`, `DEMO_BASE_URL`, `DEMO_ACCESS_CODE` or `GOOD_FAITH_CLIENT_IP_HEADER`; the first four belong to the laptop, and on Render the caller's address comes from `CF-Connecting-IP` by itself.
5. Apply. The build runs with the variables set (the server modules create their clients when they load, so the build needs them). The build log should end with the route table: `/_not-found` static, everything else (including `/`) dynamic. Node comes from `.node-version` in the repo (`22`, the laptop's major version), so Render doesn't move to a newer default between deploys; Next.js 16 needs 20.9 or newer. A `NODE_VERSION` variable in the service's Environment would override the file.
6. Why Starter and one instance: the free plan sleeps after 15 minutes without traffic, and a judge's first page would wait about a minute for it to wake. The wrong-code limit on the access page is counted in memory, so one instance keeps one count.
7. What Render does not limit: there is no 4.5 MB body cap and no per-route time limit, so the `maxDuration` exports in the routes (written for Vercel) are ignored, and an inspection or a close-out run takes as long as Claude does (well under a minute each in testing). The app keeps its own 4 MB upload budget (section 8) whatever the host allows.
8. The URL is `https://good-faith.onrender.com` (or the name Render gives if that one is taken). A custom domain is optional.

On Vercel instead: the app runs there too (the routes declare their `maxDuration`, and the browser keeps every request under Vercel's 4.5 MB body limit), but each serverless instance keeps its own wrong-code count, so the throttle in section 8 is weaker, and the sweep has to run from the laptop.

## 6. What it costs

- **Render Starter:** $7 a month for the web service. A cron job for the sweep (section 9) is billed for the time it runs. **Supabase free:** 500 MB of database and 1 GB of storage, which the demo uses a fraction of (a demo copy is a few dozen rows and no files of its own until the visitor uploads), with the seven-day pause above; Pro is $25 a month if it should stay awake.
- **PayPal sandbox:** free, fake money. Live invoicing would cost 3.49% plus $0.49 per paid invoice and Payouts carry their own fee, which is why the pitch leans on Payouts for money out.
- **Anthropic:** the only metered cost. Five things spend: a lease check (one call with the PDF), an inspection (one call per room, each with that room's photos), a close-out run (a tool-use conversation of up to twelve steps, run twice: up to the approval and after it), an advocate run (a tool-use conversation of up to eight steps, with the disputed charges' photos) and a negotiator run (one call per turn, at most six). Each is cents to a dollar on Opus depending on the PDF and photo sizes; a full demo is a few dollars at most. A demo copy itself costs nothing: it is copied in Postgres, its findings are the template's, and the closed unit's settled dispute is recorded history. Read the console's usage page after the first hosted run and set the spend limit from that.

## 7. Keeping it safe

- `.env.local` never leaves the laptop and is gitignored; Render holds the hosted secrets. There are no `NEXT_PUBLIC_` variables in this app, and the Supabase secret key must never become one: it bypasses row level security, so every query is scoped to the session's workspace in code (`src/lib/workspace.ts`, section 9).
- To rotate a key: Supabase (API Keys > the key's menu), PayPal (the app's Secret > Generate new), Anthropic (revoke, create), then update the variable in the service's Environment on Render and deploy again. `PAYPAL_WEBHOOK_ID` is not a secret (a delivery is trusted because PayPal confirms its signature, not because it names the id), but a webhook deleted and registered again gets a new id, which goes on Render the same way.
- Before any real tenant: a real sign-in for the landlord pages (the access code is one shared demo code), a privacy notice on the tenants' page, and only then the live PayPal decision in step 2.6. `PAYPAL_ENVIRONMENT=LIVE` must not be set before the sign-in exists; the close-out routes refuse it until then.

## 8. The access gate and the daily limits

The hosted demo is gated so an open URL can't spend the Anthropic key or flood the PayPal sandbox.

**The gate** (`src/proxy.ts`, `src/lib/session.ts`). Every page and API route needs a session, except `/access` and its form (`POST /api/access`, and `POST /api/access/sign-out`), the tenants' pages and their files (`/t/<token>`, `/api/t/<token>/...`, guarded by their token as before), Next's static files, and `GET /api/health`, which answers `{"ok":true}` and nothing else. A page without a session goes to `/access?next=<the page>`; an API call gets a 401 with a plain message. The right code sets a signed cookie, `gf_session`: HttpOnly, SameSite=Lax, Secure in production, seven days. It carries the kind of session (`owner` or `demo`), a session id (always `owner` for the owner, a new uuid for each demo sign-in), the workspace the session sees (`owner`, or the id of that browser's demo copy) and its expiry, signed with HMAC-SHA256. Codes are compared in constant time. Wrong codes are limited in memory (`src/lib/access-throttle.ts`): 10 per 10 minutes from one address, and a ceiling of 200 per 10 minutes across every address. Once the ceiling is reached, an address that has itself been wrong in the window waits ("Too many tries"), but one that hasn't still gets its try, so a flood of wrong codes can't lock the judges out. A restart clears those counts, which is why the codes must be long and random. The account menu has "Sign out" and, in a demo copy, "Start over" (section 9).

The address is read from a header the caller can't choose. On Render (it sets `RENDER` in the environment) that is `CF-Connecting-IP`, which Render's Cloudflare sets to the address that reached it; Render's `X-Forwarded-For` keeps whatever the caller sent as its first entry, so that entry is never used. Elsewhere the app takes the last `X-Forwarded-For` entry (the one the nearest proxy appended), or the header named in `GOOD_FAITH_CLIENT_IP_HEADER`.

Sessions can't be revoked one at a time: Sign out clears that browser's cookie, and a copied cookie stays valid until it expires. To end every session at once (a leaked cookie, a judge's code you want to retire), change `GOOD_FAITH_SESSION_SECRET` and restart; change the code too if the code itself leaked. A session whose demo copy has been swept is sent to the access page to enter the code again.

| Variable | What it does |
|---|---|
| `GOOD_FAITH_ACCESS_CODE` | The judges' code. Each browser that enters it gets a new private copy of the demo (section 9) and a demo session, with the daily limits below. |
| `GOOD_FAITH_OWNER_CODE` | Your code. Opens the owner workspace (your data, everything made before workspaces existed) with no per-session limits, but it counts toward the day's totals. Ignored if it equals the judges' code. |
| `GOOD_FAITH_SESSION_SECRET` | Signs the session cookie; at least 32 characters (`openssl rand -base64 48`). Changing it signs everyone out. |
| `GOOD_FAITH_CLIENT_IP_HEADER` | Optional. The header that carries the caller's real address on a host other than Render (for example `x-real-ip` behind nginx). Leave it unset on Render. |
| `GOOD_FAITH_ACCOUNT` | Optional. The owner workspace's account name in the sidebar and the PayPal card (otherwise the owner of the oldest tenancy). Demo copies always show Harbor View Rentals. |

How it fails: with `GOOD_FAITH_ACCESS_CODE` unset outside production (`next dev`), the gate is off and every request is the owner, so local development works as before. Unset in production, or set with a missing or short secret anywhere, every gated page says "This demo is not configured" and every gated API call gets a 503: closed, never open.

Changing a code: the proxy runs on the Node.js runtime and reads these variables from the environment on each request; `next build` does not copy them into the bundle (checked on 16.3.8: a build made with one code, started with another, accepts only the second). So a new code or secret needs a restart of the service with the new environment, not a rebuild. Only `NODE_ENV` is fixed at build time.

**The daily limits** (`src/lib/limits.ts`, the `daily_usage` table and the `take_usage` function). Each Claude job, each sandbox invoice and each new tenancy takes one unit of the day's allowance (the Pacific day), and stored uploads take one unit per started megabyte, before Claude, PayPal or storage is called; the check and the count are one locked step in Postgres, so requests that arrive together can't go past a limit. A refusal is a 429 with "Today's demo limit for this is used up. Everything already prepared still works." A job that fails before anything was spent gets its unit back: a lease check or an inspection where Claude never answered (an overload, a bad key), a close-out that failed before the agent's first call, an invoice PayPal refused to create. New demo copies have their own count (`demo_copy_usage`, counted in `create_demo_workspace` with the copy itself, so a copy that fails counts nothing): per caller address (a keyed hash of it, never the address) and in total. Defaults, each changeable on the host:

| Variable | Default | Counts |
|---|---|---|
| `GOOD_FAITH_DAILY_LEASE` | 5 | Lease checks per demo session (one Claude call each) |
| `GOOD_FAITH_DAILY_INSPECT` | 3 | Move-out inspections per demo session (one Claude call per room) |
| `GOOD_FAITH_DAILY_CLOSE_OUT` | 4 | Close-out agent runs per demo session (the approval that resumes a run is part of it) |
| `GOOD_FAITH_DAILY_INVOICE` | 5 | PayPal sandbox deposit invoices per demo session |
| `GOOD_FAITH_DAILY_TENANCY` | 10 | New tenancies per demo session |
| `GOOD_FAITH_DAILY_UPLOAD_MB` | 100 | Megabytes of photos, receipts and after-repair photos stored per demo session |
| `GOOD_FAITH_DAILY_ADVOCATE` | 3 | Runs of the tenants' advocate per tenant link (the tenants' page has no session, so it counts by link; each run is one Claude job of a few steps with the disputed charges' photos), and runs of the landlord's negotiator per demo session (each run is one Claude job of at most six calls, one per turn, three exchanges in all) |
| `GOOD_FAITH_DAILY_TENANT_UPLOAD_MB` | 20 | Megabytes of dispute photos per tenant link |
| `GOOD_FAITH_DAILY_COPIES` | 5 | New demo copies per caller address (entering the code, or Start over) |
| `GOOD_FAITH_DAILY_AI_TOTAL` | 150 | Claude jobs per day across every session, the owner's included |
| `GOOD_FAITH_DAILY_INVOICE_TOTAL` | 100 | Sandbox invoices per day across every session |
| `GOOD_FAITH_DAILY_TENANCY_TOTAL` | 50 | New tenancies per day across every session |
| `GOOD_FAITH_DAILY_UPLOAD_MB_TOTAL` | 400 | Megabytes of uploads stored per day across every session (lease PDFs are bounded by the lease limit instead) |
| `GOOD_FAITH_DAILY_COPIES_TOTAL` | 60 | New demo copies per day across every address |
| `GOOD_FAITH_INSPECT_ROOMS` | 6 | Rooms one inspection compares; more is refused before any call |
| `GOOD_FAITH_INSPECT_PHOTOS` | 6 | Photos per room and phase an inspection sends (the first ones taken) |

A refused copy says so on the access page: "This network has started the most demo copies allowed for today. Try again tomorrow." or "Today's demo copies are used up. Try again tomorrow." Start over keeps the browser's session id, so it doesn't reset the per-session limits; a new sign-in does, so the per-session limits are soft and the day's totals are the real ceiling, with the Anthropic console's spend limit (section 3) behind them. A unit is a job, not a Claude call: a lease check is one call, an inspection one call per room (up to 6), a close-out run up to twelve agent steps plus the steps after the approval. So 150 jobs can be several hundred calls. For the judging window, set `GOOD_FAITH_DAILY_AI_TOTAL` to what a day of judging needs (for example 40) and the console's limit to match. The free Supabase plan holds 1 GB of storage; the upload totals keep a day under that, but check Storage's usage now and then while the URL is public.

**Uploads** are checked on the server whatever the browser did: at most 4 MB per file and per request (the proxy answers a declared body over 4.5 MB with a plain 413 once Next has received it, keeping at most 5 MB in memory; a body sent without a `Content-Length` is cut at 5 MB and the route refuses it as unreadable), 20 photos per request, 10 after-repair photos and one receipt per deduction, 120 photos per tenancy, and every file is identified by its first bytes: JPEG, PNG, GIF or WebP for photos (and sharp must read it as the same format), PDF for leases, PDF or a photo for receipts. HEIC is refused, as before; the browser converts what it can decode.

**Headers** (`next.config.ts`): `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin` (`no-referrer` on the tenants' pages), `X-Frame-Options: DENY` with `Content-Security-Policy: frame-ancestors 'none'`, and `Strict-Transport-Security` in production.

**On Render:** the health check path is `/api/health` (set in `render.yaml`). API writes (POST, PATCH, DELETE) whose `Origin` names another host than the request's `X-Forwarded-Host` (when the host's proxy sets it) or `Host` are refused with a 403, so a page on another site can't act with a judge's session; Render passes the public host through, but if every save on a new host fails with "That request came from another site", the proxy in front is rewriting `Host`. One instance keeps the wrong-code counts in one place; with more than one, each counts its own. After the first deploy, check that the throttle sees the real address: send eleven wrong codes, each with a different made-up `X-Forwarded-For` (`curl -X POST https://<host>/api/access -H 'Content-Type: application/json' -H 'X-Forwarded-For: 203.0.113.<n>' -d '{"code":"wrong"}'`). The eleventh must answer 429 "Too many tries" (that address, yours, then waits ten minutes, so sign in first); if every one answers 401, the header the app trusts is not the one Render sets, and `GOOD_FAITH_CLIENT_IP_HEADER` needs the right name. To seed the demo against the hosted copy from the laptop: `DEMO_BASE_URL=https://<host> DEMO_ACCESS_CODE=<the owner code> npm run demo:seed`.

**Checking a production build locally:** build in a worktree (see the README's Checks), then start it with test codes on the command line, not in `.env.local`, so local dev stays open: `GOOD_FAITH_ACCESS_CODE=<test> GOOD_FAITH_OWNER_CODE=<test> GOOD_FAITH_SESSION_SECRET=<32+ chars> npx next start -p 3211`. Each sign-in with the test judges' code makes a real demo copy in the database (and takes a pre-paid deposit when the pool has one); remove them afterwards with `npm run demo:sweep -- --workspace <id> --apply`. A bare `next start` sets `X-Forwarded-For` itself, so every local browser counts as one address (`::1`) for the copy limit and reaches 5 copies quickly; the access page then says the network has started the most copies allowed. Add `GOOD_FAITH_DAILY_COPIES=50` to the command line for a local test run (or send a different `X-Forwarded-For` per test client). The day's total, though, is shared: the database counts every copy in `demo_copy_usage`, local or hosted, against `GOOD_FAITH_DAILY_COPIES_TOTAL`, so a local test run spends the hosted demo's copies for that day. On judging days, skip test sign-ins against this database, or raise `GOOD_FAITH_DAILY_COPIES_TOTAL` on Render for the window.

## 9. Private demo copies

Every browser that enters the judges' code gets its own copy of the demo landlord, made at that moment, and works in it alone (`src/lib/workspace.ts`, the `workspaces` table).

**Workspaces.** `properties` and `tenancies` carry a `workspace_id`; everything else hangs off a tenancy. One workspace is the owner's: it holds everything made before workspaces existed, and the owner code opens it. Each demo copy is a workspace of kind `demo`. The server reads with the secret key, which bypasses row level security, so the scoping is in code: every list (Properties, Tenants, Payments, Documents, Move-outs, search, the bell, the activity) filters by the session's workspace, and every page under `/tenancy/<id>` and every route that names a tenancy loads it only when it is in that workspace, answering 404 exactly as for an id that doesn't exist. The ids below a tenancy (a photo, a deduction, a run, a payment) are always looked up under it. Uploads go under `ws/<workspace id>/` in each bucket, and a page gets a signed link only for a file of its own workspace or one of the templates' files. The tenants' page (`/t/<token>`) stays scoped by its token.

**The templates** (`demo_templates`). A copy is made from three template tenancies of the owner's, one per role: `94ee6bca-...` (`closed`: 482 N. Glassell St, Unit B, California, closed out, refunded, statement delivered), `e06de0e7-...` (`move_out`: 1140 E. Juniper Hollow Ln, California, moved out, Claude's findings with their damage boxes, three deductions, ready for the refund) and `3e4598bf-...` (`notice`: 2317 Mesquite Bend Dr, Unit 3, Austin, Texas, seeded with `npm run demo:seed -- --state TX`: the tenants gave 30 days' notice to leave when the lease ends, the deposit paid through a sandbox invoice, the tenant link sent with the notice, the written forwarding address still to come). `create_demo_copy_with_history` (which runs `create_demo_copy` and then adds each template's history, section below) copies all three in one transaction: the property (with its state, so the copy follows that state's rule pack), the tenancy, payments, photos (rows pointing at the template's own storage files, never duplicated), findings, deductions, notices, the approved close-out run of the closed unit, a new tenant link token, and the activity with one entry per real step. Every date moves so the move-out unit moved out yesterday (statement and refund due in 20 days), the closed unit closed out three days ago and the Texas tenants gave notice 20 days ago (so their lease ends, and they move out, 10 days later), never earlier than the template's own dates (PayPal's dates can't move, so a copy made in the first days after the templates is dated as they are). PayPal's own records keep PayPal's dates. The templates are read only, the owner's session included: a change answers 409, `demo:seed` and `demo:reset` refuse them, and the sweep never touches them or their files (the two California templates keep theirs under `<tenancy id>/`, the Texas one under `ws/<owner workspace>/<tenancy id>/`; a copy may sign either). The older `create_demo_workspace`, which the code before the Texas unit calls, still copies the two California templates only, and `create_demo_copy`, which the code before the settled history calls, is unchanged, so each migration goes in first and the running code keeps working until the deploy. The migrations register this project's three; on a fresh project, seed three demo tenancies (in California one closed out and one stopped before the close-out, and the Texas one with `npm run demo:seed -- --state TX`) and register them:

```sql
insert into public.demo_templates (tenancy_id, role, anchor, days_ago) values
  ('<closed tenancy id>', 'closed', '<the day it was closed out>', 3),
  ('<move-out tenancy id>', 'move_out', '<its move-out date>', 1),
  ('<Texas tenancy id>', 'notice', '<the day the notice was given>', 20);
```

**The closed unit's settled dispute** (`demo_template_history`, `scripts/demo-history.mjs`). Every copy of the closed unit (482 N. Glassell St, Unit B) shows a dispute already settled: the tenants disputed the carpet and the range cleaning, their advocate's case, the negotiator's counter, the advocate's counter, the negotiator's concession, $270.00 back, accepted by the tenants and approved by the landlord, with the amended statement and a Settlement row in Payments. It is history only. The template's deposit is a payment every copy shares, so no money can move for it: the settlement carries no PayPal id, its record is marked `demo_example`, and every page that shows it says "Demo example: no PayPal money moved". The live dispute, with a real sandbox refund, runs on the move-out unit. The history is one row per template, built by `npm run demo:history` from the template's own facts: the agents' answers are written in the script as a recorded example and go through the app's own checks exactly as a live answer does (validateCase, firstTurn, runNegotiation with the two agents stubbed by the AI SDK's mock model), and the script stops if the code changed any of them. No Claude call, no PayPal call, and the template is only read. A new copy gets it in the same transaction as the copy (`copy_demo_history`), with the template's deduction ids mapped to the copy's and every date moved with the copy; a copy made earlier keeps what it has. A history that can't go in never costs the visitor their copy: it goes in under its own savepoint, so a failure (a hand-edited row, a charge it names that the copy doesn't have) leaves the copy as it was before the history existed, and the server logs `demo copy ... was made without its settled history` with the reason. Like the copy's story, its totals count the example's $270.00 as returned (the ledger, the amended statement's "Returned in all", the tenants' refund amount, Properties' Refunded this year), each beside a "Demo example" label; only a live settlement moves PayPal money. This project's row is stored; on a fresh project, after registering the templates:

```bash
npm run demo:history               # build it and check it (a dry run)
npm run demo:history -- --apply    # store it for new copies
```

**The tenants' view in a copy.** In a demo copy one person plays both sides, so each copy's tenant links can be opened from its own pages: "Open the tenant's view" under the refund on Move-out, under the delivery record on the Statement, and on the Tenants tab. A copy's link token is derived from the session secret (`GOOD_FAITH_SESSION_SECRET`) and the link's id rather than drawn at random, and the database still keeps only its hash, so a copy of the database opens nothing. With the gate off (local development, every session the owner's) there is no secret and no demo token, and links stay random. Changing the session secret ends every session, so each visitor gets a new copy anyway; in an old copy, "Open the tenant's view" no longer shows (its token can't be made again), while an old tenant URL someone kept still opens its page until Make a new link on the Tenants tab replaces the link. A real landlord's link (the owner's workspace) is random and shown once, as before.

**The deposit pool** (`demo_deposit_pool`, `scripts/demo-pool.mjs`). A copy's refund must go back against a real payment of its own, so the move-out unit's copy is made with a pre-paid sandbox deposit: the same $4,800 invoice the seed sends, paid by the sandbox tenant. Making a copy claims the oldest ready deposit (`FOR UPDATE SKIP LOCKED`, so two copies made at once never take the same one); a deposit over 170 days old is past PayPal's 180-day refund window and is skipped. Only the California move-out unit takes one: the Texas unit is copied at the notice stage and leaves the pool as it is. Its copies show the Texas template's own deposit, which a copy never refunds (`src/lib/demo-pool.ts`, `depositBlock`, which recognizes a template's invoice whether or not any other copy still points at it): its Review refund page says "In the demo this unit's deposit is one sandbox payment every copy shares, so this copy can't send its refund. Everything else works.", and the close-out route answers 409 before any Claude call. Fill it from the laptop, which needs `.env.local` with the Supabase and PayPal values, the sandbox tenant's login and a Python with Playwright (as for the seed):

```bash
npm run demo:pool -- --status      # ready, claimed, too old
npm run demo:pool -- --fill 4      # top up to 4 ready deposits (about a minute and one sandbox payment each)
npm run demo:pool -- --adopt INV2-...   # add an invoice already paid by hand as the sandbox tenant
```

Keep about as many ready as you expect judges to send refunds in a day, and check it daily during judging. Each deposit takes $4,800 of the sandbox tenant's fake balance and the refund gives $3,790 back (a settled dispute gives some of the other $1,010 back on the same payment, and the deposit stays used either way); if PayPal refuses a payment for funds, top up that sandbox account's balance in the developer dashboard. When the pool is empty, a new copy is still made and works, but its Review refund page says "Today's sandbox deposits for the demo are used up, so this copy can't send a refund. Everything else works.", Prepare refund is off, the close-out route answers 409 before any Claude call, and the server logs `demo copy ... was made without a sandbox deposit`. A copy never refunds a deposit it doesn't hold.

**Start over** (account menu, demo copies only; `POST /api/access/start-over`). The browser gets a fresh copy dated today, under the same daily copy limits. A deposit the old copy never used goes back to the pool first, so the new copy can take it, including after Prepare refund: a refund the agent only proposed, a run that failed or one that ended without sending keeps nothing, and once the deposit is back in the pool the old copy can no longer send that refund. A deposit it refunded stays used, and so does one whose close-out run is still running at that moment. The old copy's rows stay until the sweep.

**The deposit's date.** A copy's lease began about a year ago, but its deposit is a real sandbox payment made when the pool was filled, and PayPal's dates are PayPal's: the refund goes back against that payment, inside PayPal's 180-day window, so the date can't move to move-in day. The deposit's tips on Overview, Move-out and Review refund say so in a demo copy.

**The sweep** (`scripts/demo-sweep.mjs`). Removes demo copies made more than 14 days ago (a session lasts 7), with their rows (the tenants' disputes, turns and settlements among them, the closed unit's recorded one included) and their `ws/<id>/` files (the tenants' dispute photos among them), and upload folders whose workspace is gone. It never touches the owner's workspace, the templates or their files, or a deposit in the pool that no copy has claimed; a removed copy's unused deposit goes back to the pool. A dry run unless told otherwise:

```bash
npm run demo:sweep                                  # what would go
npm run demo:sweep -- --apply                       # remove it
npm run demo:sweep -- --workspace <id> --apply      # one copy now, whatever its age (a test copy)
```

Run it weekly from the laptop during judging, or as a Render cron job: `render.yaml` has the job commented out (daily at 11:15 UTC, `npm run demo:sweep -- --apply`, with only `SUPABASE_URL` and `SUPABASE_SECRET_KEY`); uncomment it, sync the Blueprint and set the two variables. On a host the script reads them from the environment when there is no `.env.local`.
